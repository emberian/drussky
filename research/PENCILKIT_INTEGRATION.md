# PencilKit writing activity in the Rust app

Decision proposal, 2026-11-06. The initial research pass used source inspection only, with no application changes, builds, model calls, signing changes or device changes. The subsequently authorized adapter implementation is described below; physical acceptance remains outstanding. One Kagi query through `/Users/ember/swarm/research.py` located the Apple PencilKit/delegate documentation and published Rust bindings; those primary sources, the actual crate source, installed SDK and current shell were then inspected. This establishes integration feasibility, not measured latency or Russian recognition quality.

## Recommendation

Present a **full-screen native writing controller for the active lesson activity**, with `PKCanvasView` owning the paper and its gestures. Keep the Rust task, progression, audio identities, cue history and persistence authoritative. Native UI renders a bounded Rust activity projection and returns typed actions/checkpoints; it does not acquire its own curriculum or assessment rules.

The controller should comfortably accommodate a whole word or short phrase. Keep the spoken-prompt/copy controls and brief meaning beside a large, stationary writing area, then offer **Save and compare → reveal/repair → Say it → another take/return to lesson** in that same activity. Hear→handwrite→repeat and see→copy→learn to say are task variants, rather than letter-shaped canvas restrictions. The visible model can be hidden/revealed without replacing the paper or discarding ink. A ruled page, pan/zoom, eraser, undo/redo and an explicit finger-writing option belong to the paper. Audio starts/ends and any separately recorded speech remain actual events supplied to Rust. These are product recommendations, not claims that this combined teaching loop is experimentally validated.

| Option | Consequence | Decision |
| --- | --- | --- |
| Native canvas over a DOM rectangle | Must synchronize CSS pixels/native points, visual viewport, safe areas, page scroll, native canvas scroll/zoom, clipping and hit testing. A web explanation opening or keyboard changing the viewport can move the paper under the Pencil. | Avoid for the first implementation. |
| Native full-screen activity controller | One coordinate/gesture owner; UIKit handles rotation/safe areas and the paper remains stationary. Some prompt/action controls are rendered natively from the same Rust projection. | Recommended. |
| Replace the app shell/curriculum with Swift | New state/persistence/navigation implementation and migration surface. | Unnecessary. |

## What the existing shell actually exposes

The pinned app uses Dioxus **0.7.10**, Wry **0.53.5**, `objc2` **0.6.5** and Apple framework bindings **0.3.2**. Dioxus `DesktopContext.webview` is public; Wry's iOS `WebViewExtIOS::webview()` returns a retained native WKWebView subclass. `apple_export_native.rs` already uses this exact route to find the containing window's root view controller and present a UIKit controller on the main thread. This is the correct scene/window anchor; do not choose an arbitrary global application window. No Dioxus/WebKit fork or injected web drawing loop is required. [Wry's extension API](https://docs.rs/wry/0.53.5/wry/trait.WebViewExtIOS.html), [Dioxus source](https://docs.rs/dioxus-desktop/0.7.10/dioxus_desktop/struct.DesktopService.html).

Prefer an iOS-only **Rust/objc2 controller plus narrow public-API bindings**. Published `objc2-pencil-kit 0.3.2` has `PKDrawing`, `PKStroke`, `PKStrokePath`, `PKStrokePoint`, inks and tools, but omits `PKCanvasView`, its delegate and `PKToolPicker`. Several UIKit variants—color constructors, stroke masks and preview-image methods—are absent too; the generated counterparts are macOS-only. Thus “add the crate and import PKCanvasView” will not compile. Bind the missing classes/protocol/selectors with `extern_class!`/`extern_protocol!`, using typed `UIScrollView`, `UIViewController`, `UIColor` and the existing data-model types. Keep those declarations in one small SDK-mirrored module, not scattered `AnyObject` messages. [Published bindings/source and license](https://docs.rs/crate/objc2-pencil-kit/0.3.2).

A thin Swift controller is technically viable, but is a second choice here: the current Xcode project **only stages/signs the already linked Rust executable**. Adding a Swift file to that signing wrapper cannot make its code callable from Rust. A real Swift route needs target-specific static-library compilation/linking during the Rust build, Swift runtime/bundle handling, simulator/device separation and source-fingerprint inputs. Reconsider if the narrow binding layer grows substantially. A future Swift-only recognizer can remain a separate tiny shim without moving curriculum into Swift.

## Availability, dependency and recognition boundaries

Installed `iPhoneOS27.1.sdk` headers confirm `PKCanvasView`/drawing archives from iOS13; drawing policy and stroke/path/point access from iOS14. Our existing iOS15 deployment floor already covers them, including the reported iPad26.4.2. `PKCanvasView` is a `UIScrollView`. Use `.pencilOnly` explicitly for Pencil mode, with a deliberate `.anyInput` toggle for finger use; native handling replaces custom web palm/pressure rendering. Physical palm rejection still needs an actual Pencil test. [Canvas](https://developer.apple.com/documentation/pencilkit/pkcanvasview), [input policy](https://developer.apple.com/documentation/pencilkit/pkcanvasviewdrawingpolicy).

Add only an iOS-target `objc2-pencil-kit = 0.3.2` dependency with explicit data/tool features, plus required existing UIKit/Foundation feature flags (`UIScrollView`, gestures, layout/controls, `NSUndoManager`, etc.). Link the OS PencilKit framework. The Rust binding license is **Zlib OR Apache-2.0 OR MIT**; Apple PencilKit remains an Apple SDK/system framework governed by Apple's SDK terms, not an open-source recognizer to redistribute. No handwriting model download is required for native capture.

`PKStrokeRecognizer` in the installed Swift interface is an **iOS/macOS27 Swift actor**, with runtime `supportedLanguages`, not an Objective-C class available through ordinary `msg_send!`. Do not call it on iPad26 or infer Russian support from locale selection. Root's separate language-capability probe must decide this optional path.

For an iPad26 recognition option, Google's official digital-ink list explicitly includes **Russian `ru`**. Its iOS guide specifies `GoogleMLKit/DigitalInkRecognition 8.0.0` via CocoaPods and downloadable models; iOS15.5 is the documented minimum, so adding it also changes our current15.0 build floor and native dependency pipeline. Recognition is on-device after model availability, but the SDK can contact Google for updates and usage/performance metrics. It is governed by Google API/ML Kit terms; the documentation's Apache sample license does not make the SDK/model Apache-licensed. Treat integration/model preparation as a separate bounded recognition adapter, not a dependency of saving ink. [Language list](https://developers.google.com/ml-kit/vision/digital-ink-recognition/base-models), [iOS integration](https://developers.google.com/ml-kit/vision/digital-ink-recognition/ios), [release notes](https://developers.google.com/ml-kit/release-notes), [terms/privacy](https://developers.google.com/ml-kit/terms).

Recognition receives the independent saved writing and writing-area geometry. Do not supply the expected answer as “pre-context,” silently autocorrect ink or turn a transcription hypothesis into spelling/legibility/mastery evidence. The learner can confirm/edit recognized words separately. [Recognition context/order guidance](https://developers.google.com/ml-kit/vision/digital-ink-recognition/ios#tips_to_improve_text_recognition_accuracy).

## Capture and acknowledged-save contract

Keep two representations: the **exact `PKDrawing.dataRepresentation()` archive** for faithful native reopening, and a **versioned portable PencilKit control-point projection** for cross-platform display/recognition. The latter is processed PencilKit ink, not a raw hardware touch stream. Preserve stroke order, path creation date/time offsets, locations, size, force, opacity, azimuth/altitude, transform and visible/masked ranges; unavailable properties are absent, not invented browser tilt/pressure values. On iOS26 do not rely on iOS27 stroke UUIDs. Keep original coordinates in paper points; viewport zoom/offset is separate metadata. Do not repeatedly rescale stored ink on rotation. A PNG is a bounded derivative preview, never the only original. [Drawing/archive API](https://developer.apple.com/documentation/pencilkit/pkdrawing-swift.struct), [stroke path](https://developer.apple.com/documentation/pencilkit/pkstrokepath).

Proposed commands are `Open(activity+scope+attempt+taskRevision+savedCheckpoint)`, `ApplyProjection`, `AckCheckpoint` and `CloseAfterAck`; native events are `Ready`, `Action`, `Checkpoint`, `Failure`, `Closed`. Every event carries controller instance, task/scope/attempt identity and monotonic checkpoint sequence. Rust accepts only the active binding, validates finite/bounded coordinates/counts/bytes and hashes both payloads before durable repository acknowledgement. Swift/Rust callbacks must enter the Dioxus-owned event receiver, rather than mutating reactive state from arbitrary native callbacks. Archives can travel directly through Rust buffers; no base64/JSON detour through JavaScript is needed.

Autosave changed drawing revisions after edits/undo/redo and before navigation/backgrounding. **Tool-end is not a final-save signal:** Apple's SDK explicitly says `canvasViewDrawingDidChange` can arrive later because final Pencil pressure is delayed, and cancellation may produce no change callback. A compare/save action pauses editing, retains the native canvas/checkpoint pipeline, and acknowledges the latest observed drawing revision. Late revisions must still be checkpointed; do not release the controller/delegate or claim a final immutable original solely on `DidEndUsingTool`. Finalization needs a tested settling protocol; a guessed fixed sleep is not evidence of final-pressure completeness. Save failures retain visible ink and permit retry. App backgrounding needs an atomic native recovery checkpoint as well as ordinary Rust persistence; next launch reconciles its exact task/hash instead of assuming an async web bridge completed. [Delegate semantics](https://developer.apple.com/documentation/pencilkit/pkcanvasviewdelegate/canvasviewdrawingdidchange(_:)).

Undo/redo uses the native canvas undo manager; semantic checkpoint revisions survive even though the undo stack need not survive app relaunch. A corrected new take gets a new attempt ID and preserves the first sealed original. Rust records reveal/replay actions at their actual occurrence; merely opening a controller creates no attempt success.

## Implementation slice and acceptance

Proposed files: new `src/handwriting_native.rs` (typed lifecycle boundary), `src/handwriting_native_ios.rs` (controller/delegates), `src/pencilkit_bindings.rs` (missing public selectors); adapt `handwriting.rs` for renderer-neutral paper/ink metadata and exact task binding; let `handwriting_view.rs` select native versus the existing browser adapter; preserve the latter for web/desktop/Android. Add target-only manifest features and focused persistence/adapter tests. No core protocol change follows merely from choosing PencilKit; any durable learning facts remain a separate reviewed contract.

Before shipping, in the repository's single build slot:

1. Compile the small binding/controller seam for device and simulator and confirm existing non-iOS builds stay free of UIKit/PencilKit dependencies. This is still unproven by this read-only spike.
2. On the actual iPad/Pencil, write whole words and a phrase, rest the palm, erase, undo/redo, zoom/pan, rotate and use split view. Paper must stay stable and native drawing remain responsive; simulator mouse input cannot establish Pencil latency/palm behavior.
3. Exercise fast pen-up→Done, delayed drawing callbacks, interrupted strokes, undo during autosave, failed/full-disk saves, duplicate/stale acks, route change and background/kill/relaunch. Reopen archive and portable preview from the acknowledged hashes; no late original may be lost or attributed to a new task.
4. Complete both hear→write→compare→say and see→copy→say with real audio callbacks, model reveal chronology and a separate retry. Restore on another client with the archive retained and a useful portable ink view. Then evaluate independent Russian recognition on actual words/phrases before presenting it as useful feedback.


## Authorized implementation checkpoint

The source slice now exists in `handwriting_native.rs`, `handwriting_native_ios.rs` and `pencilkit_bindings.rs`, with eight pure transport/binding-validation tests in `tests/native_handwriting.rs`. It uses iOS-only manifest features, exact bundled WAV bytes through native AVAudioPlayer, revisioned archive/control-point checkpoints (batched rather than every drawing frame), app-private atomic recovery journals with a resign-active checkpoint, explicit comparison resume and a pause-before-navigation API. The flow owner integrates its callback into the Rust UI actor; Rust must reject any unmet task/cue preconditions through a failed checkpoint acknowledgement **before** native comparison reveals the model. System-font models are labelled “Printed example,” not represented as the authored hand-printing/stroke-order demonstration. Compilation, native simulator interaction and physical Pencil acceptance are separate checks; this source checkpoint does not establish them.
